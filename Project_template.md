## 1. Сравнение LLM-моделей: локальные (Hugging Face) vs облачные (OpenAI / YandexGPT)

| Критерий | Локальные модели (Hugging Face, напр. Mistral, Llama 3, Qwen) | Облачные модели (OpenAI GPT-4o, YandexGPT Pro) |
|----------|---------------------------------------------------------------|------------------------------------------------------|
| **Качество ответов** | Высокое, особенно у современных моделей (Mistral, Llama-family, Falcon, Vicuna и др.), но требует тонкой настройки промптов (fine-tuning) под домен и RAG-контекста. Могут уступать GPT-4o в сложных многошаговых рассуждениях и стиле. | Лучшее качество “из коробки”, особенно GPT-4o — превосходит в точности, связности, адаптации к стилю и сложным запросам. YandexGPT Pro — хорошее качество, но слабее в англоязычном контексте. |
| **Скорость работы** | Локальные развёртывания дают низкую внутреннюю латентность при локальных запросах, но требуют GPU/оптимизации (quantization, tensor-cores) и грамотного autoscaling для нагрузки. Для больших моделей и высокой конкуренции нужна дорогая GPU-инфраструктура: на CPU — медленно (5-15 токенов/сек), на GPU — быстро (30-100+ токенов/сек). Задержка первого токена может быть высокой без оптимизации. | Облачные сервисы обычно дают гарантированную и предсказуемую латентность (SLA/edge), но зависят от сетевой задержки. Для интерактивного корпоративного бота это преимущество — меньше DevOps-работ. Задержка <1 сек для большинства запросов. |
| **Стоимость владения и использования** | единовременные/периодические CAPEX (GPU-серверы) + OPEX (электричество, администрирование). Для небольшой-средней коллекции (десятки тысяч документов) self-host может быть экономичнее в долгосрочной перспективе, но требует SRE/ML-ops ресурсов. | Оплатите за потребление (токены/запросы). Для RAG-бота с частыми короткими вызовами и embedding-запросами расчёт стоимости может быть прозрачным, но при большом трафике затраты растут. Риск роста затрат при масштабировании. |
| **Удобство и простота развёртывания** | Сложно: требуется настройка окружения, оптимизация (vLLM, llama.cpp), мониторинг, обновления. Нужны DevOps-навыки. | Очень просто: REST API, готовые SDK, документация, SLA. Минимум инфраструктурных забот. |

**Промежуточный вывод**:  
- **OpenAI GPT-4o** — лучшее качество и скорость из "коробки", идеален для MVP и быстрого старта.  
- **Локальные модели** — выгодны при высокой нагрузке, требованиях к конфиденциальности и долгосрочной экономии.  
- **YandexGPT** — компромисс, но менее предпочтителен из-за языковых ограничений (основной контент — технический, на английском).

## 2. Сравнение моделей эмбеддингов: локальные (Sentence-Transformers) vs облачные (OpenAI Embeddings)

| Критерий | Локальные (Sentence-Transformers, напр. all-MiniLM-L6-v2, e5-large) | Облачные (OpenAI text-embedding-3-large) |
|----------|---------------------------------------------------------------------|-------------------------------------------|
| **Скорость создания индекса** | Зависит от железа: на CPU — медленно (100-500 док/сек), на GPU — быстро (1000-5000 док/сек). Можно батчить. | Скорость зависит от пропускной способности API (параллелизация), обычно быстрый поток, ограничения могут быть в сетевых задержках и rate-limits. |
| **Качество поиска (релевантность)** | Хорошее, особенно у e5-large-v2 и bge-large. Но уступает OpenAI по точности семантического соответствия в сложных технических запросах. BGE v2 (large) — **64.1**, E5-mistral-7b — **64.8**, Jina AI v3 — **65.2** — почти на уровне топ-облачных.| Лучшее на рынке: text-embedding-3-large показывает state-of-the-art результаты на MTEB, особенно в retrieval для технической документации. OpenAI text-embedding-3-large — **64.9**, Cohere Embed v3 — **65.1**, Voyage-lite-02-instruct — **65.7** (лидер) — лучший для RAG с инструкциями.|
| **Стоимость владения и использования** | Условно бесплатно open-source (без лицензионных платежей). Только стоимость инфраструктуры. При большом месячном приросте документов (~400 стр./мес.) локальная обработка будет экономичной и контролируемой.| Платить только за генерацию эмбеддингов (цены на embeddings указаны в публичной документации). Для постоянной переработки документов это регулярная статья расхода. OpenAI: $0.13 / 1M токенов → ~$0.65 за 5M токенов. Voyage: $0.10 / 1M → дешевле и точнее.|

**Промежуточный вывод**:  
- Если приоритет — максимальное качество без ограничений на стоимость и быстрый запуск — самый простой путь. Voyage AI стал лидером по качеству эмбеддингов для RAG, особенно с instruction-tuning. 
- **Sentence-Transformers** — если приоритет — контроль затрат и/или конфиденциальность данных — sentence-transformers локально (all-mpnet, multi-lingual модели) + периодическая переиндексация — оптимальный выбор.

## 3. Сравнение векторных баз: ChromaDB vs FAISS vs Qdrant

| Критерий | ChromaDB | FAISS | Qdrant |
|----------|----------|-------|----------------------------------|
| **Скорость поиска и индексации** | Быстрее, чем «ручные» реализации на SQL/NoSQL, но уступает FAISS и Qdrant при миллионах векторов. Поиск: 10–50 мс на 20K векторов. Индексация: средняя. | Лидер по «чистому» ANN-поиску (особенно GPU). Поддерживает IVF, HNSW, PQ — позволяет балансировать между скоростью, памятью и точностью. Поиск: <5 мс. Индексация: очень быстрая. | Использует HNSW-граф для поиска (одна из лучших структур по соотношению точности/latency). Поиск: 2–10 мс (оптимизирован под HNSW + quantization). Отличная производительность на CPU, GPU не обязателен. Индексация идёт быстро и устойчиво, быстрее Chroma. |
| **Сложность внедрения и поддержки** | Очень низкий порог входа: pip install chromadb, Python API, интеграция с LangChain. Подходит для MVP/POC. | Сложно: Библиотека/бэкенд, а не полноценная «база». Нет встроенного хранения метаданных и REST API. Требует «обвязки» (обычно LangChain, Weaviate, Milvus используют FAISS внутри). | Умеренно: Полноценная векторная БД - REST/gRPC API, поддержка фильтрации, шардирования, репликации. |
| **Удобство в работе** | Встроенные коллекции, CRUD, хранение метаданных, простая работа с документацией. Подходит для data scientists и прототипов. | Только для статических датасетов. Нет CRUD. Хорош для кастомных решений, где DevOps/ML-ops могут сами поднять API и persistence. | Лучший UX: веб-интерфейс, полнотекстовый + векторный поиск, role-based access, фильтрация по метаданным, payload search, интеграция с LangChain/LlamaIndex. Хорошо документирован, активно развивается. |
| **Стоимость владения** | Open-source, лёгкая нагрузка на инфраструктуру, может работать на CPU. Для серьёзного продакшена может потребовать внешнее хранилище + кластеризацию.  | Open-source, без лицензий. Но для GPU-ускорения нужны дорогие карты (A10/A100/H100). | Open-source (Rust), ресурсоэффективен, может работать даже на средних CPU-инстансах. В облаке — прозрачное ценообразование.|

**Промежуточный вывод**:  
- Chroma → MVP/прототипы.
- FAISS → хайлоад, миллионы векторов, низкая latency (особенно с GPU).
- Qdrant → «золотая середина» для продакшн-систем уровня QuantumForge (десятки тысяч векторов можно легко держать Qdrant на одном узле без GPU.): удобство API, фильтрация, стабильность на CPU, не требует дорогого GPU.

## 4. Рекомендуемая конфигурация сервера для развёртывания RAG-бота
### Оценка входных данных
Документы: ≈18k MD/MDX + 3k Confluence + 250 PDF → условно 25–30k «сегментов» при разбивке на 500–1000 токенов → ~30k–60k векторов. Прирост ~400 страниц/мес. — добавлять 1–2k векторов ежемесячно. 
Полный объём: 60k × 6 КБ = ~360 МБ (очень мало для продакшн-сервера).
Нагрузка: десятки–сотни запросов в день от сотрудников (внутренняя база).
Это значит: упор не на хранение, а на отзывчивость поиска + интеграцию с RAG.
### Вариант 1 — MVP / пилот (самый простой)
CPU: 4 vCPU
RAM: 8 GB
GPU: не требуется
Диски: 50–100 GB SSD
ПО: Qdrant (Docker), OpenAI embeddings (облако), LLM в облаке (OpenAI/YandexGPT)
Подходит для старта: нагрузку выдержит, дешёво в облаке, легко поддерживать.

### Вариант 2 — Продакшн без GPU (оптимальный для задачи)
CPU: 8 vCPU
RAM: 16–32 GB
GPU: не требуется (Qdrant и Chroma оптимизированы под CPU)
Диски: 200 GB NVMe SSD (с запасом под рост базы и логи)
ПО:
Qdrant как векторная база (single-node)
OpenAI/YandexGPT LLM (облако)
CI/CD обвязка для регулярной переиндексации
Самый сбалансированный вариант: легко поддерживать, ресурсы с запасом, можно держать на YandexCloud.
### Вариант 3 — High-load / эксперименты с локальными LLM
CPU: 16–32 vCPU
RAM: 64 GB
GPU: 1 × NVIDIA A100 / A10 / H100 (если будете запускать локальную LLM, например Llama-3 70B или Mixtral)
Диски: 500 GB NVMe SSD
ПО:
Qdrant (кластерная установка)
Локальный эмбеддинг (Sentence-Transformers)
Локальная LLM (через vLLM или Ollama)
Это уже избыточно для текущих данных, но подходит, если полностью отказаться от облачных LLM (например, по требованиям безопасности или для внешнего продукта).

## Вывод
Согласно промежуточным выводам для QuantumForge Software с текущими объёмами и скоростью роста для разворачивания подходит вариант 2 (8 CPU / 16–32 GB RAM / без GPU) — оптимальный баланс цены и удобства.
Qdrant предпочтительнее Chroma/FAISS для продакшн, потому что:
есть фильтрация по метаданным (например, искать только по Confluence или по API-докам), удобный REST/gRPC API, проще поддерживать (кластер, резервные копии).
GPU-сценарий понадобится только если компания решит полностью локализовать LLM-модель.
